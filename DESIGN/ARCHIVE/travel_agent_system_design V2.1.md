## §1 产品定义

### §1.1 四象限用户场景 + 发布顺序

|          | 境外规划                  | 境内执行           |
| -------- | --------------------- | -------------- |
| **外国用户** | 海外区注册（邮箱/Apple），出发前规划 | 入境后定位检测 → 执行模式 |
| **国内用户** | 国内区注册（手机号/微信），无入境检测   | 直接执行           |

- **发布顺序决策（v1.6.1 反转）：国内区先行。** Phase 1 = CN 区（阿里云）把基本功能做通并内测；海外区（AWS 新加坡）降为 Phase 2。理由：高德数据源、POI/讲解主库、团队协作都在国内，开发摩擦最小；本地 GLM 的 GPU 在国内采购/托管更成熟；数据驻留铁律使后上海外区零数据迁移成本。**注意：备案链仍是国内区「公开上架 + 收费」的前置**——策略 = 备案链本周照常启动、与开发并行；开发期内测不受阻；若备案进度理想国内区直接首发，否则海外区可反超首发（双区同构，切换成本低）。
- **范围声明**：国内用户出境游一期不做（四象限之外，避免定位检测与 region 逻辑歧义）。

### §1.2 核心差异点

执行模式随行 Agent（重排 / 讲解——截图带不走的价值）+ **吃饭不愁**（每天午餐/晚餐时段自动插入顺路餐厅：评分排序 + 步行距离；一键领餐厅优惠、购景点门票含优惠——高德/美团 deeplink，佣金通路）+ **语音 + 拍照翻译（v1.9 · v1.9.5）**（按住说话 → 流式转写 → GLM 翻译 → TTS 播报；拍照/相册 → 端侧 OCR → 缓存/Flash/GLM-4.5V 分流，全本地不出区，P95<2s——入境游客问路/点菜/看菜单的高频刚需，免费钩子）+ **一键预订手off（v1.9）**（酒店/机票/火车票/门票：Agent 带参 deeplink 跳渠道 App 完成交易，我们只做行程上下文预填与确认卡片，不代客下单不碰资金——铁律 22）+ **退改无忧（v1.9.4）**（所有预订默认可退改选项优先，确认卡片在跳转前明示退改签规则摘要与免费退窗口截止——铁律 23：无摘要不跳转）+ **紧急卡**（110/120/119/最近警局医院/使领馆信息，纯静态本地数据，离线可用，零合规风险）。

### §1.3 商业模式

- **规划免费**（获客锚点）。
- **海外（Phase 2）**：执行期**消耗型 IAP $6.99/行程**（重排 + 完整讲解 + 误车跨天改），服务端收据校验 + webhook 退款回收权益。Stripe 仅保留给未来非数字商品，一期不上。
- **国内（Phase 1 先行）**：门票/餐厅佣金 + 增值订阅 **¥39–68/行程**（IAP 档位）。**支付通道（v1.9 定案）**：国内 Android = **微信支付 + 支付宝 App 支付双通道**（一般行业费率均约 0.6%；商户号均需企业/个体工商户营业执照——公司注册即前置，无「注册前个人收款过渡」，央行 259 号文禁止个人收款码经营性收款）；**iOS 数字商品一律 IAP**（Apple 3.1.1：中国区禁止 App 内第三方支付引导，外链授权仅美/欧/韩/日不含中国）。支付宝工程要点：异步通知 25 小时内 8 次重发须返回纯 success · 对账单 T+1（下载链接 30 秒失效）· 退款按 out_request_no 幂等、窗口一般 12 个月、退款不触发通知须主动查询。**佣金分销选型 W11 前必须完成**：国内走美团/携程联盟（Phase 1，美团联盟需企业资质），海外用户走 Trip.com affiliate（Phase 2）——这是商业模式支柱，不是可选项。
- **佣金现金流周期（v1.9.2）**：渠道佣金 **T+30 起步月度结算**（酒店佣金多为离店后结算，票务更长），而 GPU/云成本实时发生——账面盈利 ≠ 现金流健康；**预留 3–6 个月运营资金缓冲**；变现主序列 = 订阅/IAP（微信/支付宝 T+1 结算）在前、佣金（T+30+）在后；佣金收入不进一期毛利模型的保守口径不变（§6.11）。
- **付费开关化（v1.5.1 决策）**：付费基建（IAP、收据校验、权益系统）一期建成，但**何时开始收费是运营决策，全部远程配置**——付费墙总开关（支持分地区/分用户群灰度）、免费额度数、快照上限、触发时机均为服务端配置；默认策略 = 全免费，可随时灰度开启，**不需要发版**。
- **免费额度 = 每行程 1 次重排**（绑定 itinerary，不绑日历月）。
- **免费应急兜底（v1.5 新增，永远免费）**：误车/错过时免费给出「最近替代班次 + 打车 deeplink」——静态数据 + deeplink，成本近零，慌张时刻救命不收费。
- **付费墙后移（v1.5 修正）**：慌张时刻只做价值展示（免费应急兜底），付费转化推送放在**慌张解决后 30 分钟**（情绪平复 + 感激峰值）。卖「安心」（下次提前预警 + 全程自动重排），不卖「救命」——防止「绑架行程」差评反噬，评分是旅行产品的获客引擎。
- **快照版本额度**：免费 **3 版** / 付费 **10 版**（服务端配置化，不写死）。
- **iOS 必须申请 App Store Small Business Program**——2026-03-15 起中国区佣金调整：标准 30%→**25%**、Small Business/次年自动续订 15%→**12%**（Apple 官方公告，无需重签协议）；iOS 毛利建模按 12%–25% 区间。
- **单位经济硬指标（v1.5 量化）**：毛利底线 **≥65%**；**讲解缓存命中率 ≥90% 升格为核心经营指标**（缓存与否 = 亏损边缘 vs 70% 毛利的分水岭）；月度成本复核。

## §3 接入设计

- 登录双轨：海外（邮箱验证码 + Apple，禁 Google OAuth）｜ 国内（手机号验证码 + 微信）。
- **数据驻留铁律**：用户数据只落所在区，永不跨境同步。
- **参考数据同步方向定案（v1.5）**：**CN 区为参考数据主库，单向复制到海外区**（POI 几乎全是中国城市，CN 区靠近数据源）。白名单 = pois / 班次静态库 / 讲解模板 / **匿名化行程模板**（二期）。讲解文案判定为参考数据（不含用户信息），在 CN 区生成后经白名单同步，判定依据写入本节备查。
- **推送（v1.6.1 调整）**：Phase 1 国内区 = 厂商推送通道（华为/小米/OPPO/vivo 聚合或友盟），资质未齐前开发期用 App 内 WS 长连/轮询兑底；APNs/Firebase（海外区）随 Phase 2 接入。
- **境外高德可达性（v1.7 预埋，Phase 2 启用）**：高德 Web 服务 API 是平台级大陆限制（境外发起直接拒绝），海外区后端调高德必须经**大陆代理层**（阿里云大陆区，仅对海外后端 IP 白名单开放，只传查询参数不传 PII），用量日志加 `region`+`scene` 维度与 `overseas_planning_via_cn_proxy` 场景；高德 SDK 在境外设备**图面为空** → 境外规划期**不渲染地图**，用时间轴 + 列表承载（文字抽取/行程编排不碰地图服务）；`pois` 双坐标（GCJ-02 主存 + `wgs84_location` 副本）防境外地图渲染漂移。
- **多设备策略（v1.5 明确）**：last-write-wins + WS 互踢通知（「另一设备已更新行程」）。

## §4 数据模型

**原则不变：数据模型一次到位（多城），功能分期解锁（先单城）。单城也走多城写入路径。**

```sql
-- W1-2 建表（全部建齐，约束先立）
CREATE TABLE users (
  id UUID PRIMARY KEY,
  region VARCHAR(10) NOT NULL, -- 'CN' | 'OVERSEAS'（修正 VARCHAR(2) 存不下 OVERSEAS）
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW() -- 全表补审计字段
);

CREATE TABLE pois (
  id UUID PRIMARY KEY,
  source VARCHAR(20) NOT NULL, -- 稳定业务键：刷新走 upsert，UUID 永不变
  source_poi_id VARCHAR(100) NOT NULL,
  UNIQUE(source, source_poi_id), -- 防止管线刷新打断 itinerary_items 引用
  city VARCHAR(50) NOT NULL,
  name_zh VARCHAR(200), name_en VARCHAR(200),
  category VARCHAR(50), -- 含 transport_hub
  status VARCHAR(20) DEFAULT 'active', -- 关停/搬迁 → 行前体检联动
  location GEOGRAPHY(POINT, 4326),
  wgs84_location GEOGRAPHY(POINT, 4326), -- v1.7：境外地图渲染副本（Phase 2），入库时与 GCJ-02 成对写入
  updated_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_pois_location ON pois USING GIST (location);
CREATE INDEX idx_pois_city ON pois (city);

CREATE TABLE poi_hours ( -- 营业时间规则表（粒度补齐）
  id UUID PRIMARY KEY,
  poi_id UUID REFERENCES pois(id),
  rule_type VARCHAR(20) NOT NULL, -- standard | holiday | special（淡旺季/午间闭馆）
  payload JSONB NOT NULL
);

CREATE TABLE itineraries (
  id UUID PRIMARY KEY,
  user_id UUID REFERENCES users(id),
  cities TEXT[] NOT NULL,
  title VARCHAR(200),
  working_sync_version INT NOT NULL DEFAULT 1, -- 原 version 改名：技术同步计数器
  active_snapshot_id UUID, -- 执行版；NULL = 工作副本直接执行
  status VARCHAR(20) DEFAULT 'draft',
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
  -- execution_log 字段移除 → 独立表（JSONB 挂热表无界膨胀）
);

CREATE TABLE itinerary_snapshots ( -- ★ v1.5 新增：用户快照版本
```

- **版本入口（v1.5）**：时间线页/行程详情 → 保存此版（自动命名 + 备注 + LLM 差异摘要）/ 版本列表 / 基于此版继续改 / 设为执行版。恢复前工作副本有未保存改动 → 弹窗「先存一版 / 丢弃并恢复」。
- **手动编辑（v1.5）**：时间线拖拽/改时间 = 本地生成 diff op，**与 LLM 同管线校验**（铁律函数的 Dart 移植版，纯函数移植成本可控）——改个时间零 LLM 成本、零 3 秒等待，离线可用。
- **离线 = 执行模式生存底线**：行程 + **OSM/MapTiler 瓦片**（2km 走廊 ≤150MB）+ 讲解文案预下载；音频 = 预合成包可选下载（+30MB）或系统 on-device TTS 降级（解决「TTS 在线 vs 离线底线」矛盾）。
- **时区铁律（铁律 13）**：一切时间计算以行程城市时区为准，推送注册时折算——防止用户手机在出发国时区导致凌晨推送。
- **到点提醒**：geofence 动态注册（只保留下一个点，≤2 个常驻），避免常驻后台定位的耗电与审核风险。
- **通知权限 priming**：先解释价值再请求系统权限；被拒后 App 内 briefing 页兜底。
- **隐私（v1.5）**：预测偏差在端上计算，只上传聚合值；轨迹不出设备。

### §5.4 同步机制（全量覆盖，不做增量合并）

- `working_sync_version` 每次变更 +1；本地 drift 存 `sync_state(itinerary_id, last_version)`。
- 触发时机：App 前台激活 + 收到 WS 推送；本地落后即拉全量覆盖**当天及之后**的天数（铁律 12）。
- **多设备**：last-write-wins + WS 互踢通知。
- **快照**：服务端权威，本地缓存只读。

## §6 Agent 设计

### §6.0 行程变更管线（Itinerary Mutation Pipeline）★ v1.5 新增

> **铁律 0：一切行程变更——LLM 重排 / 手动拖拽 / 快照恢复 / propose_replan——产出统一 diff op，进同一硬校验管线。无例外通道。**

硬校验从「Agent 的校验函数集」升格为**独立行程域服务**，Agent 只是调用方之一。收益：手动编辑零 LLM 成本；测试只需针对一个入口；快照恢复天然复用。

### §6.1 渐进式规划（v1.5 修正澄清前置）

澄清 **≤2 问**（天数、城市）→ **立即生成带假设标注的 v0**（「假设中等节奏、不早起」，标注可见可改）→ 对话迭代。**Time-to-first-itinerary < 60s 为激活指标**。反转顺序的理由：用户在具体行程上改比回答抽象问题容易十倍；假设标注是信任建设。

### §6.2–6.3 工具循环 + 增量 diff

- 会话状态存 Redis（滚动摘要 + 单会话 token 上限触顶处理）；structured output，JSON Schema 约束。
- **Agent 运行时：工具循环自研，不引入 agent 框架**（harness 类产品经评估不采纳：定位 = 个人/开发者 agent 底座而非多租户服务端编排；工具循环刻意做薄，核心资产 = 铁律管线/CP-SAT/快照/权益皆自研域逻辑）。
- **餐饮与票务工具（v1.7）**：`recommend_restaurants(day_plan, meal_slot)`——午餐/晚餐空窗 × 顺路度 × 高德评分 × 步行距离，插入为 food 类行程项（`pois.category=food` 复用，零新表）；`get_ticket_deeplink(poi)` / 领券 deeplink——高德/美团渠道，佣金入 §1.3 分销通路；餐厅营业时间同样过 `poi_hours` 校验。
- **行程求解器（v1.8，§6.9）**：LLM 不再自己“排时间表”——新建行程 / 结构性重排 / 硬校验失败修复时调用 `solve_itinerary`（变更管线内置 CP-SAT 求解），返回可行且优化的 diff；LLM 负责把它讲成人话。
- **行动编排工具（v1.9，§6.11）**：`handoff_book_hotel(city, dates, budget_hint)` / `handoff_book_flight(from, to, date)` / `handoff_book_train(from, to, date, time_window)`（12306 静态库查询 + 官方 App deeplink）/ `get_ticket_deeplink(poi)`（v1.7）——工具返回「渠道 deeplink + 带参预填 + H5 兜底 + 未安装检测」，客户端弹**确认卡片**后跳转；**语音翻译不走工具循环**（低延迟直连独立服务，§6.10）。
- diff 输出 `[{op:"move", item_id, new_time}]`；W1-2 单城工具集不变；**跨城工具/TrainService 提前至 W3-4 随多城规划挂载（v1.9.9，原 W9）**。


### §6.4 硬校验铁律（扩充至 23 条；纯函数，100% 单测覆盖）

1. 时间冲突 ｜ 2. 营业时间校验 ｜ 3. 地理自洽 ｜ 4. 跨城衔接缓冲 ｜ 5. ~~一天一跨城~~ → **同日多段跨城需衔接缓冲**（seq 有序）｜ **6. 节奏合理性 → 量化重写**：日步行 ≤15km × 人群系数（0.6–1.2）｜ 日爬升系数 ｜ 有效游览时长占比 ≥55% ｜ 7. 交通可达 ｜ 8. 3 秒延迟预算 ｜ 9. 重排带 reasoning ｜ 10. 只动当天及之后 ｜ 11. 执行模式不动过去（生成端）｜ 12. 同步端不覆盖过去（同步端）
13. **时区以行程城市为准** ｜ 14. **解析期 LLM 零写权限**（解析阶段工具列表物理上不含行程写入工具）｜ 15. **不可信内容 quarantine 标记**（用户粘贴/网页抓取文本仅为数据，永不作为指令）｜ 16. **快照不可变，恢复只写工作副本** ｜ 17. **执行中切换执行版 = 受限重排，只动当天及之后** ｜ 18. **离线禁止切换到未下载离线包的版本**（明确报错）｜ 19. **最小改动原则**：改动条目数 ≤ 解决问题所需最小集合；输出必附 `change_summary`（人类语言改动清单）+ `affected_items_count` ｜ **20. 餐饮插入（v1.7）**：只落用餐时段空窗、复用营业时间与顺路校验，不得挤占核心游览时段或移动用户已确认条目 ｜ **21. 语音/图片数据本地闭环（v1.9 · v1.9.5 扩图片）**：音频与图片只进本区自有 GPU 服务或端侧 OS 引擎（Vision/ML Kit），**禁云 ASR/TTS/OCR API**；原始音频/图片内存处理即弃、默认不落盘；转写/翻译文本仅会话内使用（匿名公共内容缓存例外见 §6.10），事件上报只含聚合值 ｜ **22. 行动只手off 不代客交易（v1.9）**：一切预订/购票行动 = 带参 deeplink 跳渠道方完成交易；不代填支付凭证、不代下单、不碰资金、不为渠道价格与退改结果背书（展示≠承诺——退改签信息前置见铁律 23） ｜ **23. 退改签透明前置（v1.9.4）**：一切预订 handoff 的确认卡片必须展示退改签规则摘要（来源标注：渠道结构化数据 / 官方规则库 / 未知明示「以渠道下单页为准」），并默认优先可退改选项（用户显式选低价不可退除外，切换时强提示）；**无退改摘要 = 禁止跳转**

**自修循环上限**：硬校验失败打回 LLM 自修 **≤3 次**，超限降级为「半成品行程 + 人工标注」——防烧钱死循环。

### §6.5 链接解析三刀分期 + 安全架构

文字 → 图文 → 视频；粗筛 → 精读 → 确认卡片 → 分级报错 → 成本闸门。POI 匹配置信度 < 0.8 进「待确认」。**本地模型分工（v1.6）**：粗筛 = GLM-4.7-Flash（批量低清问句）· 精读 = GLM-4.5V（图文交叉验证）· 能靠 Whisper 转录文本解决的不进视觉模型（保 GPU 吞吐）。  
**注入防御架构化（v1.5）**：铁律 14/15 + **红队注入用例进评估集**（藏指令的笔记、恶意网页），每版 prompt 回归必跑。威胁模型：攻击者无需是用户，只需在公开网页埋注入文本等管线来抓。

### §6.6 成本闸门

- **匿名期（W1-2）**：device_id + IP 双维限额 + 单行程 token 上限——匿名期 /extract 是敞口成本攻击面。
- **触顶体验**：降级小模型（v1.6 起为本区 GLM-4.7-Flash）/ 缓存讲解，**不硬停服务**（慌张时刻硬停 = 最差时刻的最差体验）；GPU 队列深度告警接入云监控。
- **讲解生成管线按 POI 缓存复用**：缓存键 = POI + **poi_version** + 语言 + 时长档位；命中率 ≥90% 监控告警（商业模式前提）。

### §6.7 执行模式 Agent

- 三形态：定时推送（纯本地）/ 主动问（重排，需网络）/ 到点讲（文案预下载）。
- **重排一键确认制（v1.5）**：执行模式重排**禁止静默生效**——「我建议这样改，只动 2 个地方」+ 一键确认。慌乱中用户需要确定感，静默改行程一次清零信任。
- **免费应急兜底路径**：误车 → 最近班次 + 打车 deeplink，永远免费。
- `propose_replan` = 规划 Agent 受限子调用，走统一变更管线。

### §6.8 权益服务（Entitlement Service）★ v1.5.1 新增 / v1.5.2 升级

> **原则：付费基建前置，收费时机后置，任意场景可配。** 接口和闸门第一天就建好；何时开、在哪个场景开、对谁开、展示什么 offer，全部是规则配置，运营决策不需要发版。

**① 付费点统一查权益，禁止硬编码免费/付费**：重排额度、讲解档位、快照上限（3/10）、误车跨天改——调用前一律过权益服务。

**② 付费场景规则引擎（v1.5.2 核心）**：付费墙不是几个固定开关，而是规则表 `paywall_rules`：

```jsonc
// 一条规则 = 什么时候 + 什么场景 + 给谁 + 展示什么
{
  "name": "慌张解决后转化",
  "enabled": false, // 默认全关 = 全免费
  "trigger_event": "emergency_resolved", // 场景事件
  "conditions": { // 任意组合条件
    "delay_minutes": 30, // 事件后延时
    "region": "OVERSEAS",
    "replan_quota_used": ">=1",
    "rollout_pct": 20 // 灰度 20%（user_id 哈希）
  },
  "offer": { "product_id": "exec_pass", "copy_key": "paywall.panic_resolved" },
  "caps": { "per_trip_max": 1, "cooldown_hours": 24 }
}
```

**③ 付费场景目录（trigger_event 枚举，四阶段全覆盖，新场景 = 加枚举 + 加规则，不改代码）**：

| 阶段  | 场景事件                                                                                              |
| --- | ------------------------------------------------------------------------------------------------- |
| 规划期 | `snapshot_limit_hit`（快照超 3 版）· `narration_preview_end`（讲解试听结束）· `multi_city_unlock`               |
| 执行前 | `offline_pack_download`（下载离线包时）· `trip_day1_morning`                                              |
| 执行中 | `replan_quota_exhausted`（免费重排用完）· `emergency_resolved`（应急兜底解决后 N 分钟）· `narration_locked`（到点讲解付费档） |
| 执行后 | `footprint_review`（足迹页回忆）· `share_itinerary`（分享时）                                                 |

**④ 客户端零硬编码**：统一 `PaywallGate` 组件——任何场景只上报「事件 + 上下文」，服务端规则引擎匹配后返回「展示哪个 offer / 不展示」，客户端只负责渲染。**新增付费场景 = 后台加一条规则**；调整时机 = 改 conditions。

**⑤ 安全阀**：`caps` 频次上限 + 冷却期兜底（任何场景每天最多弹 N 次）；规则表全部改动留审计日志；`kill switch` 一键全局关闭。

**⑥ 默认策略 = 全免费**（所有规则 `enabled=false` + 额度放宽）；开启时按 `rollout_pct` 灰度放量，观察转化与差评率再全量。

**⑦ 匿名期即落 entitlement 数据**（device_id 维度 shadow user，登录后迁移合并）——从第一天就有额度消耗与权益留痕，未来开启收费时转化漏斗基线数据已在。

**⑧ IAP 工程闭环**：消耗型商品 → 服务端收据校验（iap_transactions 留痕）→ entitlement 激活 → webhook 退款/撤销 → entitlement 状态回收。

**⑨ 与成本闸门的关系**：权益服务管「**能不能用**」（商业闸门），成本闸门管「**烧不烧钱**」（成本闸门），两者独立、都要过。

### §6.9 行程求解器（v1.8 新增：运筹优化落地）

> **分工铁律：LLM 管“理解与选点”，求解器管“可行与最优”。** 行程排期本质是带时间窗的排序/调度问题（VRPTW 同族），不该让 LLM 猜；选点与偏好理解也不该让求解器做。来源：供应链优化 12 运筹利器评估（2026-10），逐项裁决如下。

| 评估项                                      | 裁决           | 理由                                                                   |
| ---------------------------------------- | ------------ | -------------------------------------------------------------------- |
| **OR-Tools CP-SAT**                      | **✅ 采纳（一期）** | 调度/排产类国际竞赛常胜、免费商用、Python 原生与 FastAPI 同栈；区间变量 + 时间窗 + 软硬约束建模与行程排期同构   |
| Timefold Solver                          | ⏳ W9-10 评估   | 实时增量重排（秒级、不整体重算）契合执行模式 propose_replan；但 Java 栈为主，先验证 OR-Tools 不够用再引入 |
| VROOM + OSRM                             | ❌ 拒绝         | 路径/距离一律走高德 API（许可隔离 + GCJ-02 数据一致性）；引入 OSM 路网 = 第二路网源，违反 §2 地图分层铁律   |
| RL4CO（强化学习求解）                            | ❌ 暂不         | 毫秒级近优解适合高频动态派单；内测并发量级远不需要，过度工程，二期后观察                                 |
| PuLP / Pyomo / CVXPY / HiGHS / PySCIPOpt | ❌ 不采用        | LP 建模框架对本场景不如 CP-SAT 贴切；HiGHS 仅当 CP-SAT 出现性能瓶颈时的备选                   |
| pymoo（多目标）                               | 🔭 二期探索      | “少走路 vs 节奏 vs 评分”的帕累托权衡滑杆（给用户 2-3 个方案选）是真实需求，一期不做                    |
| CP-SAT Primer                            | 📚 团队教材      | W0-W3 建模学习资料（github.com/d-krupke/cpsat-primer）                       |

**架构位置与流程**：

- **位置**：`solve_itinerary` 是**行程变更管线（§6.0）的内置求解后端**，不是旁路——LLM diff（轻改动）与 CP-SAT 解（结构性变动）都从同一入口过铁律 0-23 硬校验，solver 解**不是免检通道**。
- **触发**：① 新建行程 v0 ② 结构性重排（跨天/多点移动/执行模式 propose_replan）③ 硬校验失败修复（替代 LLM 自修循环的第一优先级）④ 餐饮插入的最优位置计算（铁律 20）。
- **建模要点**：区间变量 = 行程项（start/duration 可选域）；硬约束 = 营业时间窗、不重叠、跨城缓冲（铁律 6/7）、节奏上限（铁律 6 量化）、住宿城市；软目标 = 总绕行最小 × 用户钉死点不动（铁律 19）× 高分餐厅优先（v1.7）。
- **降级链**：CP-SAT 超时（预算 3s，铁律 8）/ 不可行 → 回落现有 LLM 自修 ≤3 → 半成品 + 人工标注（原路径不变）；求解器故障只影响“生成”，不影响已存行程（与 GPU 故障同级降级）。
- **收益**：可行性由数学保证（不再靠 LLM 试错）；自修循环触发率下降 → **直接省本地 GLM GPU 吞吐**（呼应 §2.1 成本模型）；“顺路”从启发式变成可优化目标。

### §6.10 语音翻译（v1.9 新增）

> 交互（v1.9.5 起双输入模）：**① 按住说话** → 松手 → 流式转写 → GLM 流式翻译 → TTS 流式播报；**② 拍照/相册翻译**（菜单/路牌/店招/票据）→ 端侧 OCR → 分流翻译（见下）。界面同步显示原文/译文双语大字卡（嘈杂环境/听障友好，可复读/复制/一键换语言对）。目标 **端到端 P95 < 2s**。选型依据：全本地 ASR+TTS 调研（2026-10-18，10 ASR + 6 TTS 候选逐项核实许可证，底稿 `_v19_research/voice_stack.md`）。

| 环节  | 选型                                       | 要点                                                                                                                              |
| --- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| ASR | **Qwen3-ASR-0.6B**（Apache-2.0）           | vLLM 原生流式（与现有节点同栈，官方 serve 封装一条命令起服务）；zh/en/ja/ko/yue 单模型全覆盖（粤语分港/粤口音）；精度不足升 1.7B（权重 ~4.7GB）                                    |
| 翻译  | **GLM-4.6 / 4.5-Air**（现有主力）              | 流式输出**首句即送 TTS**（不等整段）；思考模式关闭；ASR 增量文本可预热翻译请求                                                                                   |
| TTS | **Fun-CosyVoice3-0.5B-2512**（Apache-2.0） | Bi-Streaming（text-in + audio-out 双流）首包低至 150ms，text-in 流式天然衔接 GLM 流式输出；9 语 + 18 中文方言（含粤语）；Seed-TTS 评测 zh CER 1.21 / en WER 2.24 |

- **延迟预算（推断，非实测）**：ASR 尾块 0.3–0.8s + GLM 首句 0.2–0.6s + TTS 首包 0.10–0.15s + 调度 0.1–0.3s ≈ **1.2–1.8s**。**POC 必测三数（W3-4）**：Qwen3-ASR 流式尾块 / GLM 首句延迟 / TTS 首包，目标卡实测。
- **降级链**：ASR 尾块超预算 → paraformer-zh-streaming（FunASR Docker，600ms chunk 行为确定，zh/en 够一期，二期换 Fun-ASR-Nano/MLT-Nano）；TTS 首包/音色不达标 → Qwen3-TTS-12Hz（官方 97ms 首包，10 语，无粤语）；粤语质量不达标 → 二期粤语单独评估（GPT-SoVITS 流式首包 3–4s 只适合预生成）；GPU 无余量 → Fun-ASR-Nano GGUF CPU + MeloTTS（CPU 实时）极限兜底。**XTTS-v2 禁商用（CPML）直接排除**；SenseVoiceSmall 权重为非 OSI 自有许可，仅作离线对照。
- **端侧降级层（v1.9.3）**：离线/弱网/GPU 拥塞不硬报错——①端侧短语包（Top 高频句式预置译文，零边际成本，<100ms）；②平台离线引擎：iOS Translation 框架 / Android ML Kit 离线翻译与文本识别（OCR）+ Speech 本地识别 + 系统 TTS——**OS 端侧能力非云 API，不出设备，天然满足铁律 21**。**定位（v1.9.9 修正）**：MVP 阶段端侧引擎 = **语音主链路**（ASR/TTS 无服务端依赖，零 capex）；本地底座就位后回归「降级层」定位（质量一致性/方言/流式是服务端强项）；最低 OS 版本、语言对覆盖、噪声环境质量 POC 实测后定一期/二期档位；不达标则仅保留短语包 + 在线标注（回到 v1.9 基线）。
- **翻译缓存（v1.9.3）**：旅行翻译内容分布极度集中（高频短语占大头；同一家餐厅菜单被无数游客拍过）→ ①短语级缓存；②菜单翻译缓存（键 = POI + 菜单文本哈希 + 语言对，失效复用讲解缓存的 poi_version 模式）。**命中即跳过 GLM**（语音链路 = ASR → 缓存译文 → TTS），零 GLM 成本、<100ms。**铁律 21 例外声明**：缓存仅存通用短语与菜单文本的匿名译文（无用户标识、不可回溯个人）；用户个人转写/翻译文本仍仅会话内使用——「公共内容 vs 个人数据」分界写入实现规范与评审清单。
- **拍照翻译（v1.9.5，输入模之二：菜单/路牌/店招/票据/说明卡）**：拍照/相册 → **端侧 OCR 先行**（iOS Vision / Android ML Kit 文本识别：离线、免费、<300ms）→ 置信度分流：① 高置信短文本 → 查翻译缓存（菜单场景：同一家餐厅被无数游客拍过，§6.10 菜单缓存天然承接，命中即出）→ 未命中走 GLM-4.7-Flash（短句直译）；② 低置信 / 复杂版面（手写菜单、竖排、书法招牌、低光低清）→ **GLM-4.5V 精读**（§2.1 视觉角色的第二用武之地：版面理解 + 翻译一体）。**不走 agent loop**（同语音链路原则）；延迟目标：端侧 OCR + 缓存命中 **<500ms** ｜ 常规链路（OCR + Flash）P95 **<1s** ｜ 复杂版面（4.5V）P95 **<3s**（拍照场景用户预期宽于对话，仍是快车道）；呈现 = 双语卡片 + 原文区块 ↔ 译文高亮对应（AR 实时叠加二期）；隐私 = 图片与音频同口径（铁律 21：内存处理即弃、默认不落盘、不出区、禁云 OCR——端侧 OS 引擎不算云）。
- **部署（规模化阶段生效，v1.9.9）**：与 vLLM 同节点独立容器（ASR ~4GB + TTS ~4GB，24G 卡可共存或独占一张小卡）；LiteLLM 路由不动，ASR/TTS 走独立服务端口；讲解音频预合成（§5）复用同一 TTS 服务。
- **MVP 形态（v1.9.9，零 capex）**：ASR/TTS/OCR 全走端侧 OS 引擎（铁律 21 依然成立：音频/图片不出设备），翻译文本走智谱云 GLM（与聊天同通道）；P95 目标以 POC 实测定档；**全本地流式管线（Qwen3-ASR + GLM 流式 + CosyVoice3）= 本地底座就位后的升级项**（音色/方言/流式质量提升），上条部署要点随之生效。
- **语言**：一期 zh↔en；二期 ja/ko/粤语（模型已覆盖；粤语在 CV3 走方言 instruct 非正式语言标签，质量 POC 验证）。
- **隐私与合规（铁律 21）**：音频不出区、禁云 ASR/TTS API；原始音频内存处理即弃、默认不落盘；语音按敏感个人信息对待（个保法）——首次使用明示同意 + 系统设置单独开关；事件上报只含聚合值（语言对/时长档，`voice_translated`）。
- **商业定位**：免费高频钩子（入境游客问路/点菜核心痛点）；不进付费墙（规则引擎可配、默认全关）；成本走 §6.6 成本闸门（语音会话独立限额，防 GPU 敞口）。**变现闭环（v1.9.3 显性化）**：翻译 = 行程期最高频触点 → 「附近评分高的餐厅，帮我订一个」→ 餐饮 handoff 佣金（§6.11）——一次 ¥80 晚餐 ~6% 佣金 ≈ ¥5，覆盖该用户数月翻译边际成本（本地 GPU 摊销口径更低）；**翻译按「零成本基础设施」设计**：用户感知到的是好用，不是翻译本身。

### §6.11 行动编排（v1.9 新增：从「说给你听」到「带你去办」）

> **边界（铁律 22）：只做带参 deeplink 手off，不做代客交易。** 我们提供行程上下文（城市/日期/班次/站点）与确认卡片；交易在渠道方 App/官网完成，价格与退改结果归属渠道方（但退改签规则必须前置展示——铁律 23，见下「退改签保障」）；不自建交易、不碰资金、不代填支付凭证。调研底稿 `_v19_research/booking_channels.md`。

**代客交易边界论证（v1.9.8 备查——「用户确认了，为什么不代客」）**：

1. **确认 ≠ 责任转移**：授权免除的是「未经授权」，不免除执行过失——代客模式下错单、重复扣款、渠道风控拦截全是执行方责任；支付环节用户在场本身就是法律与安全的底线，不是可以优化掉的摩擦。
2. **碰资金 = 二清红线**：代收代付资金池无支付牌照即违规（本项目连个人收款码经营性收款都不碰，§1.3/§3.3；代客资金池高三个量级）；保管用户渠道支付凭证/登录态 = 平台协议禁止 + 安全责任无限。
3. **渠道未开放代客下单**（v1.9.6 核查）：美团/携程/去哪儿对第三方 agent 仅 CPS 转链 + 订单同步；绕过接口用自动化模拟用户下单违反平台协议，联盟账号连坐封禁 = 佣金通道一起死。
4. **责任主体漂移**：代客下单使我们从推荐方变成经营方——出票失败/到店无房/退改纠纷的第一责任全在我方，2–3 人团队客服体系接不住；「价格与退改归属渠道方」（铁律 22/23 配套）是刻意划下的责任边界。

**优势的真相：在决策，不在执行。** 懂行程上下文、并发比价、比退改条款、把结果讲成人话——这些在 handoff 模式下已全部交付；带参 deeplink 预填已消除大部分执行摩擦（只剩支付一步）。ACP 的标准设计（商户保持 record of record、支付走用户自己的钱包授权）恰好印证：即使为 agent 交易而生的协议，形态也是「用户在 agent 流程里付钱」，不是 agent 替用户付钱——代客交易的终局在 ACP/UCP 落地，而非现在的模拟下单。

**重新评估触发器（不修改铁律 22，触发即评估）**：① 任一主要 OTA 接入 ACP/UCP 或开放合规的 agent 下单 API → 立即评估升级（供应链适配层扩展位已预留，v1.9.6）；② B2B 批发/API 直连（如同程艺龙开放平台类）成为真实商业选项 → 那是「自己变成 OTA」的重资产模式（垫资/库存风险/独立合规评审），与行程助手定位冲突，按新业务线单独立项论证，不属铁律 22 修订范畴。

**佣金通道架构（v1.9.6：四层管线，来源「佣金通道」调研经独立核查修正）**：

> **现实边界（截至 2026-10 调研，渠道商务确认）**：美团/携程/去哪儿对第三方 agent 仅开放 **CPS 转链 + 订单同步**，无代客下单 API——与铁律 22「只手off 不代客交易」天然一致：我们本来就不该代客下单，这是约束不是损失。**国际方向（已核实）**：ACP = Stripe 与 OpenAI 2025-09-29 发布的开源规范（Apache-2.0，商户保持 record of record；Visa/Mastercard/PayPal 建并行轨道）；UCP = Google 同类开放标准（ucp.dev，Mastercard Agent Pay 采用）——中国 OTA 均未接入，**供应链适配层预留 ACP/UCP 扩展位**：接入后可从「跳转归因」升级为「agent 闭环交易」而不换架构。

- **L1 Agent 编排（供应链选择）**：①**品类路由**（渠道映射 v1.9.0 内的选择逻辑）：高星/商旅 → 携程系 · 经济型/本地生活 → 美团 · 出境/外国用户 → Trip.com（Phase 2）——各家优势库存区间；②**并发比价**（二期形态，一期单渠道）：同一查询并发打多家，单渠道超时/挂掉只降级返回其余结果（对齐 §6.12 降级哲学，禁整体失败）；③**佣金推荐伦理**：排序不得按佣金高低（价格相近而佣金不同时选高佣 = 短期多赚长期毁信任）——对齐「评分只是排序信号」原则；渠道间差价幅度以实测为准。
- **L2 供应链适配层**：统一抽象接口 `searchHotel / getDetail / generatePromoLink / queryOrder / getCommission`（对齐 §8 TrainService 抽象先例）；各家字段/签名/状态机差异在适配器内抹平（签名规则以各联盟官方文档为准，实现期核对）；新增渠道 = 新增 adapter 不动核心逻辑；ACP/UCP 扩展位预留（上）。
- **L3 订单归因（佣金能否落袋的关键）**：①**一切展示给用户的可点击链接必须经转链接口处理**（带推广位/归因参数），禁止直接放原始商家链接；②**跨 App 归因断链**：用户「先点我们的链接、后自己打开美团/携程 App 下单」是漏损主场景（携程系用户直接开 App 下单比例高），W9-10 deeplink 实测同步验证归因有效性；归因窗口参考 Trip.com 官方值 **web 30 天 / App 仅 7 天**（App 端更短 = 漏损重点，签约前逐家确认）；③**订单同步**：轮询起步（量小且稳）→ 回调推送（需公网 HTTPS 回调地址，FastAPI 现成）；酒店订单状态机长（预订→支付→入住→离店→结算→退款），每步都要接住。
- **L4 结算对账**：①**计佣基数** = 用户实际消费且核对无误的订单总额（取消单/未入住不计佣）；②**预估佣金 ≠ 实结算**（技术服务费/审核扣减），以结算佣金字段为准，签约前索要到手比例测算表；③**退款逆向跨月追踪**：酒店取消链路可能跨周跨月，佣金回收等上游状态回传——action_handoffs 状态机扩展（v1.9.4 退改字段已备），对账表支持跨月；④佣金不进一期毛利（保守口径不变，§1.3）。
- **与既有模块关系**：12306 班次静态库照旧只读查询，购票动作 = handoff（交易分离不变）；`get_ticket_deeplink`（v1.7）并入同一编排层；紧急卡打车 deeplink 同模式；行动不进行程变更管线（无 diff，只落 action_handoffs 埋点）。

### §6.12 延迟与并发治理：快慢双车道（v1.9.1 新增）

> 来源：「agent 并发延迟」讨论稿（2026-10-18，`DESIGN/agent 并发延迟.rtf`）。**用户感知的「慢」有三个来源，解法完全不同**：① **Agent 多轮循环**（架构问题）——每轮 = LLM 推理 + 工具执行，8 轮跑下来一两分钟就没了，这不是算力不够，是流程长；② **GPU 并发排队**（资源问题）——LLM 每个请求实打实占显存与算力，与传统 Web 服务「边际成本近零、水平扩容」有本质区别，高峰期「想半天」里相当一部分是在排队等 GPU，不是在思考；③ **简单任务走了重流程**（设计问题）——「翻译一句菜单」和「重排整个行程」塞进同一条多轮推理管道，是产品架构偷懒，不是技术极限。**核心结论：解法不是「让一切变快」，而是分流——把快的做到极致、把慢的藏到后台。** 哪怕算力翻十倍，8 轮 agent loop 依然比一次直达调用慢；continuous batching / KV cache / 推测解码是持续红利（§2.1），但不替代架构分流。

**① 请求分类闸门（LLM 之前的闸门）**：一切用户请求先过三级分类——**规则匹配**（高频句式直接命中）→ **意图缓存**（键 = 意图 + 参数哈希，TTL 失效）→ **GLM-4.7-Flash 意图分类**（毫秒级）——再按 lane 路由；分类不确定 → 默认升舱重流程（宁可慢不可错），误判率进 §7 指标。**目标：≥80% 请求不触达主力模型**（Flash 不算主力）。依据：旅行 query 分布极度集中（「长城怎么去」「我不吃辣」「这个多少钱」占绝大多数）→ 缓存命中率天然高；真正需要深度推理的请求天然发生在「人在酒店、有 WiFi、不赶时间」的时刻——**行程是晚上规划的，不是站在街头规划的**。

**② 快车道（秒级——用户站在街头的那一瞬间，永远只碰快车道）**：

| 请求类型          | 频率    | lane 方案                                                                                             |
| ------------- | ----- | --------------------------------------------------------------------------------------------------- |
| 翻译（菜单/路牌/对话）  | 最高频   | §6.10 全本地流式管线（P95<2s，不走工具循环）+ **端侧降级层与短语/菜单缓存（v1.9.3：命中零 LLM、离线可用）** + **拍照输入 = 端侧 OCR 起步（v1.9.5）** |
| 「我在哪 / 怎么去酒店」 | 高频    | 高德确定性导航 API + LLM 只做自然语言外壳（Flash 一轮直答，禁工具循环）；**转向导航（turn-by-turn）= deeplink 跳高德 App**（不嵌高德 SDK——Key 永不进客户端 + 许可隔离 + 离线底线，§2；同 §6.11 handoff 模式；应用内画线 = OSM 瓦片 + 高德 Web API 路径数据）                                                        |
| 「附近有什么好吃的」    | 中频    | 缓存 + 推荐排序（§6.2 `recommend_restaurants`），LLM 只理解意图                                                   |
| 到点讲解          | 执行期高频 | 讲解缓存命中 ≥90%（§6.6）+ 离线预下载（§5）——命中 = 零 LLM 延迟                                                         |

**③ 慢车道（分钟级可接受——异步任务化 + 完成通知）**：结构性重排（跨天/多点移动/执行模式 `propose_replan`）、批量链接解析、讲解全量生成、行前体检扫描 → **Redis 异步任务队列 +「规划中，完成后通知你」+ 厂商推送**。用户对后台任务的耐心阈值完全不同——不会站在 ATM 前等一份年报。边界：**v0 生成仍走交互式**（TTI<60s 激活指标不变，§6.1——渐进式 + 流式 + CP-SAT 兜住）；执行模式重排推送的是**确认卡片**，不静默生效（§6.7 不变）；夜间空闲算力优先消化慢车道批量任务（§2.1）。

**④ TTFT 口径（流式贯穿一切生成路径）**：用户感知的不是总时长，是**首 token 时间**——翻译/讲解/重排说明全部流式输出、边生成边显示，首字一出「等」的痛苦就消失大半。预算：快车道 TTFT P95 <1s；慢车道「已受理」反馈 <3s（铁律 8 预算内）。

**⑤ 与现有架构的接口（不重复建设——本节只新增三件东西）**：模型分级路由 = LiteLLM + §2.1 硬件档位；吞吐手段 = prefix caching + continuous batching（§2.1 已有）；砍掉 LLM 试错循环 = §6.9 求解器（自修循环触发率下降 = 直接释放并发容量）；成本与队列治理 = §6.6。**新增 = 请求分类闸门 + 慢车道异步任务队列 + TTFT 指标口径**，其余是既有能力的重新编排。

**⑥ Obsidian 知识库的边界（备查）**：Obsidian 是**团队文档层**（runbook / GPU 扩容决策留痕 / 事故复盘），对运行时并发延迟**零直接作用**——它不在 App→API→LLM 任何一环上。产品侧承担「知识库」角色的是**缓存 + bge-m3 RAG（pgvector）+ 规则引擎**（v1.8.1 已定：产品架构不引入 Obsidian）。间接价值 = 缩短**人**定位问题的时间（降级链 runbook、容量决策记录、快慢车道命中分布复盘）+ 把「哪类 query 走哪条 lane」的运营结论沉淀成文档反哺分类规则迭代——属运维效率，不属性能工程。

**⑦ 容量基线（万级 DAU，v1.9.10）——「直接操作」刻意做轻，压力集中在「生成」**：

- **交互操作零/轻后端**：手动编辑 = 端上 diff 校验（零服务器零 LLM，§5）；翻译 = 端侧 OS 引擎 + 短文本（§6.10）；讲解 = 缓存命中（后置段）。万级用户的「操作」本身不构成压力——重负载全部在「生成」，而生成已被闸门 + 双车道治理（本节 ①–③）。
- **量级推演（量级估算，W7-8 压测校准）**：万级 DAU → 峰值同时在线 10–20% ≈ 1–2k WS 长连（单机异步可承载，横扩路径已备）；主力模型调用 = 规划/重排低频场景 + 闸门 ≥80% 不触达 → 日调用万级以内；Flash/短翻译 = 日数万；其余吃缓存。
- **四个真实压力点与对策**：①**云 API 配额/成本**——TPM/并发商务谈判（真实用量作筹码）+ LiteLLM 限流排队 + 慢车道削峰 + 量/成本阈值触发本地底座（万级正是预期触发区，v1.9.9）；②**API 层横扩**——无状态 FastAPI + Redis 会话/WS 注册表天然多实例 + SLB（单机起步竖扩，万级演练触发横扩）；③**PG 连接与慢查询**——pgbouncer 连接池前置 + execution_events 按月分区已备 + 慢查询监控；④**CP-SAT 并发求解吞吐**——独立 CPU worker 池 + 3s 预算 + 结构性重排走慢车道异步；W3-4 spike 实测并发吞吐。
- **验收锚点**：W7-8 万级容量演练（分类闸门命中率 / TPM 配额与排队深度 / 降级链切换）内测前完成。

## §7 评估体系

- **北极星指标（v1.5 修正）：行程时间预测准确率**（预测 vs 实际偏差，**端上计算只传聚合值**）。「执行模式周留存」降为结果指标——它掉了你不知道哪环断了，不可操作。
- 因果链：付费转化 ← 慌张采纳率 ← 信任 ← 前几天预测准 ← 预测准确率。它是唯一可操作的北极星。
- 过程指标：**TTI <60s**（激活）、规划→确认转化、**慌张解决后 30 分钟付费转化**、重排采纳率（联动 `affected_items_count`——改动数 vs 采纳率是质量信号）、离线可用率、**讲解缓存命中率 ≥90%（M3 讲解上线后适用，v1.9.9 后置）**、月度毛利复核。
- 每轮交互落 `agent_traces`；**prompt 文件化 + 版本号落 traces，评估集回归测试**（含红队注入用例）。
- 评估飞轮：执行偏差按城市/POI 类目/时段聚合 → 校准 `estimate_travel_time` 与节奏量化阈值。

## §9 路线图与阶段安排（国内区先行；人力假设 2–3 人：1 Flutter + 1 后端/Agent + 0.5 数据/合规）

### §9.0 阶段划分逻辑（v1.9.7 新增：必要性 × 运营成本收益 × 开发难度）

**五条排序原则**：

1. **确定性优先于生成式**——纯函数与缓存（铁律校验/快照/手动编辑/讲解缓存）先于 LLM 重流程（重排 Agent/自修循环）；CP-SAT 先于 LLM 试错。
2. **变动成本最小化优先（v1.9.9 反转）**——MVP 零 capex：云 API 按 token 付费（智谱云 GLM，v1.9.2 单位经济公式直接适用）+ 端侧 OS 引擎（ASR/OCR/TTS 免费）+ 纯函数/缓存；本地 GPU 底座 = 量触发的规模化投资（底座建成后回到固定成本复用逻辑：边际≈0 功能搭车）。
3. **零现金流风险变现先行**——CPS 转链（开发轻、不垫资、不碰资金）→ 支付订阅（微信/支付宝 T+1）→ 佣金订单同步自动化（T+30 月结、对账开发重，随量起做）。
4. **高风险早 POC**——语音三数 / CP-SAT spike / 渠道 deeplink 真机实测 / 归因有效性，全部前置到所属阶段第一周；不达标走降级链，不阻塞主线。
5. **基建前置、开关后置**——权益服务/付费墙规则引擎/远程配置第一天建好；何时收费、对谁开 = 运营决策不发版。

**阶段定义（运营视角）**：
- **M0 最小成本启动期（W0–2）**：零 capex——云 API + 端侧引擎 + 建表全量 + 合规底座（备案走已备案模型简化登记）；产出 = 评测达标（云 API 上跑）+ 数据底座；无用户面功能。
- **M1 规划核心（多城）+ 翻译钩子（W3–6）**：产品闭环与最高频免费钩子同窗口落地——多城规划免费 = 获客锚点，翻译 = 行程期活跃引擎；边际成本全部压在缓存与纯函数上（讲解资产沉淀后置 M3）。
- **M1.5 客户端工作流启动（v2.1 定档，与 M2 并行）**：后端 M1 域服务已提前交付（2026-10-18，PR#5：多城规划 Agent / 变更管线 / CP-SAT / 快照 / 翻译 / 餐厅推荐，283 测全过）；**用户功能测试通过 = 客户端开工信号**——Flutter 脚手架 + 铁律 Dart 移植（同源测试）→ 时间线页 + 版本 UI → 翻译页（端侧引擎实机 POC）→ 内测包；工程架构见 §5.0。
- **M2 执行与留存（W7–10）**：护城河（执行模式/离线/紧急卡）+ 佣金起步（CPS 转链，零垫资）+ 正式内测放量；高峰并发治理（慢车道）就位。
- **M3 变现、上架与底座（W11+）**：支付双通道 + 联盟签约 + 公开上架（默认全免费，灰度开）；现金流主序列 = 订阅在前、佣金在后；**本地 GPU 底座启动（量/成本阈值触发）+ 全本地语音升级 + 讲解管线 v1（后置段）+ 自建口径备案补办**。
- **M4 规模化（二期）**：海外 Phase 2 放量 + 佣金通道深化（订单同步自动化）+ 模板飞轮/协作/小程序。
