# 功能缺口分析与开发计划 — ChinaTrip vs 市场 & 圆周旅迹

日期：2026-10-23  
基准：本仓库代码现状（feat/v24-trip-center, d1092ce）对比  
① 16 个热门 OSS 旅行仓库（TREK 14.9k★、AdventureLog 3.8k★、itskovacs/trip 2k★、surmai、LetsFG、JourniOne、travel-plan-viz 等）  
② 主流消费级 AI 旅行产品（Mindtrip、Layla、Wonderplan、GuideGeek、携程 TripGenie/问道、马蜂窝 AI、同程程心、Wanderlog、TripIt、Tripadvisor）  
③ CRThu/pypitravel（圆周旅迹行程查看器+Excel 导出器，4★，与本系统互补非竞品）

成本标尺（单人开发）：S ≤ 2 天；M ≤ 1 周；L > 1 周。  
重要度：高 = 直接决定行程能否"带走/用起来/传出去"或明显差异化；中 = 体验增强；低 = 锦上添花或数据源不可控。

---

## 1. 结论摘要

- 我们的强项恰好是多数纯 LLM 规划器的弱项：**社交链接→POI 理解、地址+开放时间落库、12306 真实车次、确定性排程（CP-SAT + 铁律校验）、四态行程中心**。
- 最大短板集中在"**行程的出口**"：不能导出、不能分享、不能离线、不能协作——行程做完就被锁在 H5 里。
- pypitravel 值得抄的只有三件：行程链接导入（**解析对象是圆周旅迹 pitravel.cn，与携程无关——探活已证实**，见 §4.1）、样式化 Excel 导出、地图按天筛选+表图联动。
- 明确不追的：应用内真实交易闭环（OTA 巨头专属）、人流/热度数据（国内无可用数据源）、实时逐向导航。

**重要修正**：原假设「pypitravel 导入携程行程」不成立——pypitravel 全仓库零 ctrip 字样，它解析的就是圆周旅迹自家行程。**优先级反转：圆周旅迹导入先行（协议已摸清，成本 M~~L 降为 S~~M）；携程降级为"拿到真实分享链接再评估"；穷游/同程/去哪儿出局；飞猪观察。**

E2E 正向验证仍需：① 一条真实圆周旅迹分享链接（拿全量 JSON 定解析样例）；② 一条真实携程 App 分享链接（判携程可行与否）。

**在线版补充探活（同日）**：pitravel.cn 平台本身是带「贴链接→服务端解析→进度轮询」的完整行程平台（iOS App + PC Web，Vue3 + 腾讯云 WAF/Tengine；前端 bundle 提取 158 个 `/api/slytherin/` 端点，绝大多数需登录）。其链接解析 API `v2/pcweb/link/detail_v2` 被 WAF 拦截、`v1/get/batch_get_link_parse_progress` 需鉴权（406）——**它的"贴链接解析"能力不对第三方开放，不能当解析通道复用**；可借鉴的是产品形态（服务端解析 + 进度轮询）。定性：行程查看/规划层面互补，「链接解析」层面与我们同构（弱竞品）。

### 4.2 城市 POI 底库（城市→SITE 清单 + 时段属性）— import 资源矩阵与自建路径（2026-10-23 三路调研）

**背景（本地现状判词）**：现规划链路 = 现场高德 `search_poi("景点")` 每城仅 8 条 + LLM 挑选（plan.py:1710/1832-1889），**推荐本身无本地库 grounding**，高德失败还落占位假 POI（plan.py:1723-1734）；`pois` 表只是地址/营业时间副产品缓存（无评分/标签/简介/建议时长、无全量采集、app/ 零种子数据）；行程全部会话现生成、零模板。**结论：现成可合法 import 的国内城市模板库不存在；day-by-day 模板可做但优先级低（用户拍板 2026-10-23：非不能做，是暂不排期）——现阶段以城市→SITE 清单 + 时段特殊属性（如夜景须晚上）达标，自建模板（快照飞轮等）排 P2/P3。**

**三源自建操作详情**：

**① OSM — 底库主源（ChinaTravel 10 城之外的覆盖主力）**

- 下载：`download.geofabrik.de/asia/china.html`，china-latest.osm.pbf 全量约 1.5GB、**日更**；嫌大可按省下 subregion 分片。
- 处理链：`osmium tags-filter` 取 `tourism=attraction / tourism=museum / amenity=restaurant / amenity=cafe` 等 → 转 CSV/JSON → **WGS84→GCJ-02 偏移转换**（对齐高德坐标系）→ 多源合并 upsert。
- 字段产出：名称/坐标/类别/地址（部分）。中文名覆盖不均：头部景点好，小店常只有英文名或缺中文名。
- 许可（ODbL）注意：可商用，但**含 OSM 数据的库本体若对外再分发，须同样以 ODbL 开放**——只影响「把 POI 库给别人下载」的场景，业务代码和服务不受影响。
- 明确没有：开放时间（`opening_hours` 标签稀疏）、评分、热度、建议时长——全靠回源链路补。
- 坑：Overpass API 国内访问慢且不稳，**一律本地 dump 过滤，不要在线查**。

**② 文旅部 5A 名录 — 权威校准层**

- 两个来源：官方数据服务 `sjfw.mct.gov.cn` 有 5A 数据集免费下载（**无坐标**）；GitHub `tuansuwu/china-5a-scenic-areas` 已整理 **373 个 5A**（中英名 + WGS84 坐标，CC BY-SA 4.0）。
- 更新节奏：文旅部年度公布（新增/摘牌），名录会变动，按年同步。
- 用途：①**必保白名单**——全国顶级景区权威集合，这些 POI 的开放时间/时长回源优先级最高；②**查全率校验**——5A 不在合并后的底库里 = 采集漏了，直接告警补采。
- 限制：仅 5A 级，4A 及以下无带坐标权威版；CC BY-SA 有署名 + 同许可分享义务。

**③ FSQ OS Places — 餐厅补充源（可选，后置）**

- 规模：1.04 亿条全球 POI（2024 开源），中国有一定量但密度不及欧美。
- 下载：S3 parquet 月更，全量约 11GB（按国家/bbox 过滤裁剪后小得多）；**2025-10 起需注册 token**。
- 许可：免费商用 + 需署名 + **禁再分发数据本体**。
- 产出：餐厅/咖啡馆名称+坐标+类别；**无开放时间字段**。
- 定位：OSM 中国小店稀 → 餐厅维度的量级补充；国内餐厅的权威数据（评分/营业时间/人均）仍靠高德回源，FSQ 只管「发现」不管「详情」。

**④ 权威内容源评估（用户点名补充，2026-10-23）：Lonely Planet 与米其林指南**

- **Lonely Planet：❌ 不采用，性价比为负**。①中国业务已撤：2024-06 关闭中国办公室、中文内容停更，官网中国仅列北京/香港（洛阳页 404），二线城市覆盖缺失；②条款明文封杀：网站条款（2026-01-27 生效）禁止爬取/复制/商用并**专项禁止 AI/ML 训练与 RAG grounding**（正是我们的用法）；③内容授权为企业级洽谈制、无公开报价，中小项目够不上；④内容错位：LP 强项英文长简介，我们要的中文/建议时长/细粒度 tags 恰是其弱项。简介字段替代维持原案：维基百科（CC BY-SA）+ 高德/携程详情回源。

**顺带发现（已拍板采纳，2026-10-23）**：**黑珍珠餐厅指南**（美团/点评官方榜单，中国餐饮权威性与覆盖最优，引用店名级合规）——✅ **已采纳为本土品质标签层**，与米其林同款路径：榜单店名 → 高德匹配 → 打 `black_pearl`（含钻级）标签 → **每月检查重拉**（上游年度发榜，月检足够，与米其林错峰时段）。⚠️ 只采店名/钻级/城市等事实字段，**不采信黑珍珠页面简介文字**（美团系 ToS + 爬虫胜诉判例）；简介统一走 Wikidata/维基百科（CC BY-SA）+ 携程详情回源，且简介随回源周期持续更新。

**Tripadvisor 复议（用户拍板 2026-10-23）：✅ 采纳为兜底补充层（最后一位）**。角色：**仅补其它所有源（ChinaTravel/OSM/5A/高德/携程/黑珍珠/米其林）都未收录的 POI**——补差不是全量，配额压力与 attribution 负担最小化。刷新：每日重拉当批兜底条目（实时拉取+当日刷新即满足其 24h 缓存政策）。合规：展示这些条目时必须带 TripAdvisor logo+署名+回链。依赖：Content API 审批/档位与中国数据量级实测中，结果回来后定配额档位（见下方出局条目复议备注）。

**day-by-day 现成数据（用户关切：有现成的最好）**：**合法可商用的国内 day-by-day 行程数据不存在**——ChinaTravel 的 2000+ 条是排程评测查询（非成品多日行程，POI 沙盒本身可用）；TravelPlanner 1,250 条纯英文非中国城市；TripTailor 有真实行程但无 license（保留权利）；马蜂窝/携程/穷游路书有 day-by-day 但 UGC 版权 + 反爬强 + ToS 禁抓（国内有爬虫入刑判例），**勿批量抓**；Wikivoyage zh 无行程章节；OSS 仓库全是空库（TREK 仅 demo-seed 数条）。**替代方案（零额外成本，现阶段执行）**：暂不存死模板——`pois` 底库带坐标 + best_visit_time，「距离近的放一天」正是现有 CP-SAT solver 的地理聚类强项（§2 排程引擎行），每次规划即产出当天最合理的 day-by-day，比抄别人模板更贴合天数/体力/交通实况；后续若做模板，以此产出 + 快照飞轮沉淀为自建来源（可做，优先级低，P2/P3）。

**自建路径（推荐，含自我更新闭环）**：

**总原则（用户拍板 2026-10-23）：所有外部源数据（ChinaTravel/OSM/5A/米其林/FSQ/后续任何源）仅作候选与骨架，入库前（或入库后首轮回填时）必须经高德/携程回源校验**——存在性（关店/闭园剔除）、名称匹配（CITY_ALIASES + 模糊匹配）、坐标校准（GCJ-02 对齐）、时间敏感字段（开放时间/门票/时长）一律以高德/携程为准。外部源只管「发现」，存活性与详情的真相归回源链路。

1. `pois` 表扩字段：rating / tags / intro / **best_visit_time（枚举 morning/afternoon/evening/sunset/sunrise/any + 依据来源）**
2. 底库冷启动：ChinaTravel 10 城仅取**名称+坐标+类别**种子 + OSM 补其余城市 + 5A 校准，多源合一 upsert（复用 `PoiDetailStore.upsert`）；开放时间/门票/建议时长不采信任何静态源，全部回源自建；注意其 POI 名无别名机制，入库须套自家 CITY_ALIASES
3. `refresh_pois.py` 从「只补 hours」升级为「按城全量发现 + 高德/携程回源补评分/热度/营业时间」→ 自我更新闭环（OSM 日更增量 + 回源实时）；**建议游玩时长**自建采集：扩 `CtripHoursReader` 抓携程 sight 页「建议游玩时长」字段 + LLM 常识标注兜底（知名 POI 可靠性高）
4. **时段属性回填三层**（本需求核心）：①类别启发式（夜市/夜街/酒吧街→evening，山岳/观景台→sunset/sunrise）→ ②LLM 常识批量标注（知名 POI 如外滩夜景、泰山日出可靠性高）→ ③携程 sight 页/高德详情回源校验（复用 CtripHoursReader）
5. **品质标签（米其林，已采纳）**：`michelin-my-maps` CSV → 过滤中国 → 名称+坐标匹配高德 POI → 打 `michelin`/`bib_gourmand` 标签（tags 字段）→ 每月重拉；推荐侧优先展示必比登
6. 规划改造：`_collect_candidates`/`_select_pois` 先查库、缺则回源回填；城市清单从硬编码 CITY_ALIASES 升级为目录表；**solver 消费 `best_visit_time`——夜景自动排晚上（行程中心悬案就此落地）**；推荐排序对 michelin 标签做品质加权

成本：POI 底库（含时段属性）M；规划改造 S~M（模板层可做但优先级低，暂不排期）。
